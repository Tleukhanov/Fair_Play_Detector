# План реализации: Fair Play Detector

## 1. Цель проекта

Создать сервис, который по нику Lichess:

1. получает публичные партии пользователя;
2. сохраняет PGN и метаданные в базу;
3. рассчитывает признаки шахматного поведения;
4. оценивает вероятность аномального поведения ML-моделью;
5. формирует объяснимый вердикт с помощью LLM;
6. показывает результат в веб-дашборде.

Продукт не должен заявлять, что доказывает читерство. Корректная формулировка результата:

- `low_risk` — заметных аномалий не обнаружено;
- `suspicious` — обнаружены статистически необычные паттерны;
- `high_risk` — совокупность признаков сильно похожа на машинную игру.

Итоговый скор является сигналом для дополнительной проверки, а не основанием для наказания игрока.

## 3. Границы MVP

В первую версию включить:

- сканирование публичных рейтинговых партий Lichess;
- ограничение количества партий, например 20–50;
- поддержку одного контроля времени: rapid или blitz;
- базовые Stockfish-признаки;
- базовые временные признаки;
- XGBoost-классификатор с результатом вероятности;
- асинхронную обработку;
- один итоговый LLM-вердикт;
- страницу результата со статусом, скором, графиками и списком подозрительных партий.

Не включать в MVP:

- анализ приватных партий;
- автоматические обвинения или публикацию результатов о других людях;
- обход ограничений Lichess;
- real-time анализ текущей партии;
- обучение сложной нейросети на малом объёме данных;
- автоматическую модерацию аккаунтов;
- биометрические, сетевые или аппаратные признаки.

## 4. Архитектура

```text
Next.js
   |
   v
FastAPI --------------------> PostgreSQL
   |                              |
   |                              +-- users/scans/games/features/verdicts
   |
   +--> Redis queue --> ingest worker --> Lichess API
   |                         |
   |                         +--> PGN parser
   |
   +--> analysis worker --> Stockfish/Maia --> feature store
   |
   +--> scoring worker ---> XGBoost + SHAP
   |
   +--> explanation worker -> LLM adapter
```

Каждый этап должен быть идемпотентным. Повторный запуск сканирования не должен дублировать партии и должен переиспользовать уже рассчитанные признаки, если версии движка и модели не изменились.

## 7. Конвейер сканирования

### Этап A. Валидация запроса

1. Нормализовать ник: trim, Unicode normalization, регистр.
2. Проверить допустимость формата.
3. Проверить лимиты: максимум партий, частоту запросов, допустимые time controls.
4. Создать запись `scan`.
5. Вернуть клиенту `scan_id` и статус `queued`.

Ошибки должны быть явными: неизвестный пользователь, превышение rate limit Lichess, временная ошибка источника, пустой набор партий и ошибка анализа не должны маскироваться успешным ответом.

### Этап B. Получение партий

Использовать официальный экспорт Lichess:

- передавать `username`;
- запрашивать PGN-поток;
- задавать `max`, `since/until`, `perfType`, `rated`;
- уважать HTTP 429 и заголовки rate limit;
- использовать exponential backoff с ограниченным числом попыток;
- сохранять исходный PGN и хэш;
- не хранить токены или приватные данные.

Для стримингового ответа обрабатывать партии по одной, чтобы не держать весь экспорт в памяти.

### Этап C. Нормализация PGN

Проверить:

- корректность заголовков;
- наличие ходов;
- поддерживаемый вариант;
- совпадение ника пользователя хотя бы с одним цветом;
- отсутствие дубликата;
- корректность результата и времени.

Некорректную партию не удалять молча: записывать причину пропуска в telemetry и связывать её со сканированием.

### Этап D. Расчёт признаков

Для каждого хода пользователя сохранить:

- номер хода;
- FEN до хода;
- сыгранный ход в UCI/SAN;
- оценку позиции до хода;
- оценку после лучшего хода;
- оценку после сыгранного хода;
- centipawn loss;
- был ли ход top-1/top-3;
- время на ход, если доступно;
- глубину/лимит анализа;
- оценку Maia;
- вероятность выбора сыгранного хода Maia.

Агрегировать на уровне партии:

- средний, медианный и 90-й перцентиль centipawn loss;
- top-1 и top-3 match rate;
- match rate по сложным позициям;
- количество тактических ошибок;
- стабильность centipawn loss;
- долю ходов с одинаковым временем;
- медианное и среднее время на ход;
- дисперсию времени;
- корреляцию времени с трудностью позиции;
- дивергенцию от Maia;
- результаты отдельно для дебюта, миттельшпиля и эндшпиля;
- разницу между выигранными и проигранными партиями.

Важно: анализировать только позиции, где оценка движка стабильна между соседними глубинами. Удалять или отдельно маркировать шумные позиции, матовые позиции и форсированные ходы.

## 8. Признаки и защита от ложных срабатываний

Основные подозрительные паттерны:

- необычно высокая точность на сложных позициях;
- высокая доля top-1 ходов при низком уровне игрока;
- низкий centipawn loss в тактических позициях;
- почти одинаковое время на ход;
- отсутствие зависимости времени от сложности;
- сильное отклонение от Maia;
- резкий сдвиг качества относительно исторического профиля игрока.

Не считать сами по себе доказательством:

- один красивый ход;
- высокий процент совпадений в дебюте;
- игру после подсказок/подготовки;
- короткую выборку;
- партии с низким количеством ходов;
- игры с неполными временными метками;
- открытые дебютные линии;
- рейтинг противника без контекста.

Минимальные фильтры:

- не скорить выборку меньше 10 пригодных партий;
- не строить сильный вывод по партии короче 12 ходов;
- исключать bullet из первой версии;
- отдельно учитывать рейтинг, контроль времени, цвет и результат;
- использовать калибровку вероятностей;
- показывать доверительный интервал и объём выборки.

## 9. Подготовка датасета и обучение ML

### Источники данных

Сформировать два класса:

1. **Human** — публичные партии игроков с согласованным стабильным профилем.
2. **Engine-like** — партии, сыгранные Stockfish/Leela через контролируемый генератор, с разными силами, глубинами и временными ограничениями.

Не называть второй класс «доказанными читерами». Это синтетический proxy-класс для обнаружения машиноподобного поведения.

### Ограниченный и безопасный сбор датасета

Сбор выполнять отдельной командой `collect-dataset`, а не при старте API или worker. После подготовки Parquet и отчёта команда обязана остановиться; обучение модели в этом запуске запрещено.

Жёсткие параметры первой загрузки:

- **Human:** ровно один календарный месяц архива Lichess Elite;
- **Engine-like:** ровно один сезон TCEC;
- общий лимит всех скачанных байт: **не более 5 GiB** (`5 * 1024^3`), включая сжатые архивы и поток ответа;
- лимит проверять по фактически полученным байтам, а не только по HTTP `Content-Length`;
- при достижении лимита немедленно остановить загрузку с ошибкой `DATASET_QUOTA_EXCEEDED`;
- не начинать следующий источник, если preflight показывает, что общий лимит будет превышен.

Месяц Elite и сезон TCEC задаются явно параметрами, например `LICHESS_ELITE_MONTH=YYYY-MM` и `TCEC_SEASON=<season>`. Если параметр не задан, команда должна остановиться до сетевой загрузки и показать, что требуется указать, а не выбирать период молча.

#### Потоковая обработка и защита диска

1. Перед загрузкой проверить свободное место и выполнить preflight источника.
2. Не делать `download -> распаковать архив целиком`. Читать HTTP-ответ чанками и передавать его в потоковый декомпрессор (`gzip`/`bz2`/`xz`/`zstd` по фактическому формату).
3. Парсить PGN по одной партии из распакованного потока.
4. Сразу извлекать только нужные фичи: eval-профиль по ходам, время на ход, совпадение с top-1/top-3 ходом, класс и минимальные метаданные.
5. Не записывать полный PGN на диск. Если библиотеке нужен временный объект, использовать bounded `SpooledTemporaryFile` и удалять его сразу после анализа партии.
6. После закрытия каждого источника проверять, что временный каталог пуст; сырые PGN и архивы не сохранять.
7. Писать фичи в Parquet через ограниченные row groups с compression `zstd`; CSV запрещён.
8. Сначала писать во временный Parquet, затем атомарно переименовать его в итоговый файл после проверки схемы.
9. При ошибке сети, формата, дискового лимита или парсинга закрывать stream, удалять временные файлы и возвращать ненулевой код завершения.

Результат:

```text
data/processed/
├── lichess_elite_YYYY-MM_features.parquet
├── tcec_<season>_features.parquet
└── collection_report.json
```

В `collection_report.json` сохранить периоды и URL, байты по каждому источнику и сумму, количество прочитанных/обработанных/пропущенных партий, причины пропусков, размеры и хэши Parquet, схему и версию фичей.

#### Обязательная остановка после сбора

После создания обоих Parquet агент обязан остановиться и показать отчёт, не запускать обучение или дальнейшую обработку автоматически. Отчёт должен содержать:

1. количество партий каждого класса: `human` из Lichess Elite и `engine_like` из TCEC;
2. баланс в абсолютных значениях и процентах;
3. количество и причины пропущенных партий;
4. фактический объём скачанных данных и размер Parquet;
5. пример **ровно 5 строк** объединённого набора фичей;
6. названия колонок и первые значения, подтверждающие отсутствие PGN;
7. предупреждение о дисбалансе классов.

Пример формата:

```text
Сбор завершён без обучения.
Human (Lichess Elite, YYYY-MM): N партий
Engine-like (TCEC, season): M партий
Баланс: human X.X%, engine-like Y.Y%
Скачано: Z MiB / 5120 MiB
Пропущено: K партий (причины: ...)

Первые 5 строк фичей:
| class | game_id | move_count | mean_cpl | top1_match_rate | mean_move_time_ms | maia_divergence |
| ...   | ...     | ...        | ...      | ...               | ...               | ...              |
```

Только после явного подтверждения этого отчёта разрешать построение train/validation/test. Отчёт и пример строк должны читаться из Parquet и `collection_report.json`, а не быть вручную подставленными значениями.

### Разбиение

- разделять train/validation/test по игрокам, а не случайно по партиям;
- не допускать попадания партий одного пользователя в разные выборки;
- проверить распределения по рейтингу, контролю времени и длине партий;
- сохранить датасет с версией и хэшем.

### Базовые модели

1. Logistic Regression как интерпретируемый baseline.
2. XGBoost как основная MVP-модель.
3. Calibrated classifier для вероятностного результата.

Метрики:

- ROC-AUC;
- PR-AUC;
- recall при фиксированном низком false-positive rate;
- precision для класса `high_risk`;
- Brier score;
- calibration curve;
- стабильность по рейтингам и time controls.

Порог `suspicious` и `high_risk` выбирать по validation, а не вручную после просмотра теста.

### Версионирование

Для каждого скоринга сохранять:

- `model_version`;
- список признаков;
- версию Stockfish/Maia;
- параметры анализа;
- дату обучения;
- хэш датасета;
- пороги классификации.

## 10. Контракт backend API

Запрос:

```json
{
  "username": "example",
  "max_games": 30,
  "speed": "blitz",
  "rated_only": true

```

Ответ `202 Accepted`:

```json

```

Возвращает статус, прогресс, количество найденных/обработанных партий, текущий этап и ошибку при наличии.

После завершения:

```json
{
  "scan_id": "uuid",
  "username": "example",
  "risk_level": "suspicious",
  "risk_score": 0.87,
  "confidence_interval": [0.78, 0.93],
  "games_analyzed": 27,
  "summary": "Наблюдаются статистически необычные признаки...",

    {

      "value": 0.87,

      "weight": 0.34

```

Возвращает пагинированный список партий с агрегатами и ссылкой на Lichess.

Возвращает данные для графика по ходам: оценка, CPL, top move, время, Maia probability.

## 11. LLM-объяснение

LLM получает только проверенные структурированные данные:

- итоговый score;
- доверительный интервал;
- размер выборки;
- top features;
- сравнение с baseline;
- несколько наиболее показательных партий;
- ограничения анализа.

LLM не должен:

- самостоятельно менять risk score;
- придумывать факты, которых нет в JSON;
- использовать формулировку «игрок точно читер»;
- раскрывать системный промпт;
- выдавать персональные данные;
- заменять численный классификатор.

Ответ валидировать через Pydantic. При ошибке схемы выполнить ограниченный retry с исправлением формата. Если LLM недоступна, показать детерминированный шаблонный вердикт и явно указать, что пояснение сформировано без LLM.

## 12. Frontend-дашборд

### Основной экран

- поле ввода ника;
- параметры сканирования;
- предупреждение о публичном анализе и вероятностном характере результата;
- кнопка запуска;
- история последних сканирований.

### Экран процесса

- текущий этап;
- progress bar;
- `games_found/games_analyzed`;
- понятные статусы ошибок;
- автоматический polling с остановкой после `completed/failed`.

- risk badge;
- числовой score и доверительный интервал;
- число партий;
- краткий LLM-вердикт;
- список evidence;
- график CPL по партиям;
- график top-move match rate;
- график времени на ход;
- график Maia divergence;
- таблица топ подозрительных партий;
- блок ограничений и методологии.

Графики должны показывать исходные единицы измерения и не использовать визуальные эффекты, создающие впечатление абсолютной уверенности.

## 13. Безопасность, этика и ограничения

- принимать только публичные данные Lichess;
- ограничить rate limit на пользователя и IP;
- валидировать username и все UUID;
- не логировать полные PGN в обычные application logs;
- скрывать токены и ключи через environment variables;
- добавить TTL или удаление сырых данных по политике хранения;
- не индексировать результаты поисковиками;
- не показывать сканирование третьего лица как подтверждённое обвинение;
- добавить страницу методологии и disclaimer;
- предусмотреть ручное удаление сканирования;
- добавить audit log для доступа к результатам.

## 16. Нефункциональные требования

- API не блокирует HTTP worker во время анализа;
- один анализ имеет общий deadline;
- ограничить concurrency Stockfish по числу CPU;
- не допускать неограниченного роста очереди;
- повторный запрос статуса безопасен;
- большие PGN не попадают в обычные логи;
- все внешние вызовы имеют timeout;
- миграции обратимо применимы на ранних этапах;
- UI остаётся usable на мобильной ширине.

## 17. Риски и меры

| Риск | Последствие | Мера |
|---|---|---|
| Ложные обвинения | Репутационный и этический ущерб | Disclaimer, confidence interval, низкий FPR, запрет формулировки «доказано» |
| Синтетический engine-like датасет плохо похож на реальные случаи | Низкая переносимость модели | Несколько движков/сил, human baseline, мониторинг drift |
| Разные настройки Stockfish меняют score | Несопоставимые результаты | Версионирование engine config и кэш-ключей |
| Lichess rate limit | Неполный ingest | Backoff, лимиты, явный partial result |
| Слишком дорогой анализ | Высокая задержка/стоимость | Ограничение партий, кэш, depth/time budget, очередь |
| Maia недоступна | Pipeline не завершается | Интерфейс адаптера и маркировка отсутствующих признаков |
| LLM галлюцинирует | Неверное объяснение | Structured output, grounding, schema validation, fallback |
| Data leakage в ML | Завышенные метрики | Split по игрокам и проверка дубликатов |

## 18. Definition of Done

Проект считается готовым к MVP-релизу, если:

- новый пользователь может запустить сканирование по нику;
- партии загружаются только из публичного Lichess API;
- повторный запуск не создаёт дубликаты;
- pipeline асинхронен и отображает прогресс;
- минимум одна версия модели воспроизводимо обучается;
- сбор датасета ограничен одним месяцем Lichess Elite и одним сезоном TCEC;
- общий сетевой объём сбора не превышает 5 GiB;
- PGN обрабатывается потоково и удаляется сразу после извлечения фичей;
- итоговые признаки хранятся в Parquet, а не в CSV;
- после сбора показаны количества партий по классам, баланс и ровно 5 строк фичей, после чего pipeline остановлен до подтверждения;
- score сопровождается объёмом выборки и ограничениями;
- LLM не влияет на численный score;
- результат объясним через top features;
- есть обработка пустого набора, rate limit и ошибок движка;
- backend, worker и frontend покрыты smoke/integration тестами;
- Docker Compose поднимает локальный стенд;
- документация описывает запуск, конфигурацию, методологию и этические ограничения.

## 20. Протокол работы через субагентов

Разработка в репозитории `https://github.com/Tleukhanov/Fair_Play_Detector` должна выполняться не одним большим агентом, а через координатора и несколько специализированных субагентов. Координатор отвечает за декомпозицию, синхронизацию, review, разрешение конфликтов и финальный merge.

### Правила делегирования

- Перед началом работы координатор создаёт задачи с чёткими границами ответственности.
- Каждый субагент работает только в своей области и не переписывает чужие модули без согласования.
- Для каждой задачи используется отдельная ветка:
  `agent/<area>/<short-task>`.
- Каждый субагент обязан сделать один или несколько небольших атомарных коммитов.
- Коммит должен содержать понятное сообщение, например:
  `feat(ingest): add streamed Lichess archive reader`.
- Субагент не должен сам вливать свою ветку в `main`.
- Субагент обязан передать координатору:
  - что изменено;
  - какие файлы затронуты;
  - какие команды проверки запущены;
  - результаты тестов;
  - известные ограничения;
  - список commit SHA.
- Нельзя считать задачу готовой только по наличию кода: обязательны тесты и проверка контракта соседних модулей.

### Роли субагентов

#### 1. Архитектор/координатор

Ответственность:

- превратить этот план в backlog;
- определить зависимости задач;
- назначить субагентов;
- зафиксировать API, схемы данных и версии контрактов;
- следить за соблюдением лимита 5 GiB и остановки после сбора датасета;
- принимать или отклонять результаты;
- выполнять merge только после review.

Координатор не должен параллельно менять код, который уже разрабатывается другим агентом, если это не согласованный конфликт-фикс.

#### 2. Backend/Data agent

Ответственность:

- SQLAlchemy-модели и миграции;
- PostgreSQL-схема;
- репозитории и сервисы доступа к данным;
- идемпотентность партий и сканов;
- хранение статусов pipeline;
- тесты моделей и миграций.

Граница: агент не меняет UI и ML-алгоритм, кроме согласованных DTO и типов данных.

#### 3. Ingest/Streaming agent

Ответственность:

- Lichess Elite и TCEC adapters;
- потоковая загрузка и декомпрессия;
- общий byte counter;
- preflight;
- лимит 5 GiB;
- удаление PGN и временных файлов;
- `collect-dataset`;
- `collection_report.json`;
- тесты quota, truncated stream, retry и cleanup.

Граница: агент не запускает обучение и не сохраняет сырые PGN.

#### 4. Chess Analysis/Feature agent

Ответственность:

- адаптер Stockfish;
- адаптер Maia;
- потоковый PGN parsing;
- eval-профиль;
- время на ход;
- top-1/top-3 match rate;
- schema Parquet;
- версионирование feature set;
- fixture-тесты анализа.

Граница: агент не меняет классификатор и не выбирает пороги риска.

#### 5. ML agent

Ответственность:

- dataset loader из Parquet;
- очистка и проверка качества данных;
- split по игрокам;
- baseline;
- XGBoost;
- calibration;
- метрики и model artifacts;
- feature importance/SHAP;
- regression tests для model output.

ML agent начинает обучение только после того, как координатор подтвердил отчёт безопасного сбора: два Parquet существуют, лимит соблюдён, показаны классы, баланс и ровно 5 строк фичей.

#### 6. FastAPI/API agent

Ответственность:

- FastAPI application;
- `POST /api/v1/scans`;
- endpoints статуса, verdict и games;
- Pydantic-схемы;
- worker state machine;
- OpenAPI;
- API integration tests;
- явные ошибки и таймауты.

Граница: агент использует утверждённые backend/ML contracts и не меняет frontend напрямую.

#### 7. Frontend agent

Ответственность:

- Next.js application;
- форма запуска сканирования;
- экран прогресса;
- polling;
- экран verdict;
- графики и таблица подозрительных партий;
- loading/empty/error states;
- frontend tests и accessibility.

Граница: агент не вычисляет risk score на клиенте и не дублирует ML-логику.

#### 8. LLM/Explanation agent

Ответственность:

- LLM provider adapter;
- строгая Pydantic-схема объяснения;
- prompt versioning;
- grounding только на численных признаках;
- fallback без LLM;
- prompt contract tests;
- запрет формулировки «доказано читерство».

#### 9. Infra/QA agent

Ответственность:

- Docker Compose;
- CI;
- lint/type-check/test commands;
- observability;
- resource limits;
- smoke tests;
- проверка, что worker не оставляет зависшие scans;
- проверка дисковых лимитов и очистки временных файлов.

#### 10. Security/Privacy agent

Ответственность:

- проверка секретов и environment variables;
- rate limits;
- валидация входных данных;
- безопасные логи без полного PGN;
- политика retention/delete;
- проверка внешних URL и архивов;
- privacy/ethics review.

Этот агент не исправляет всё молча: он сначала выдаёт список findings с severity и confidence, после чего координатор создаёт отдельные fix-задачи.

### Порядок параллельной работы

1. Архитектор/координатор фиксирует контракты, структуру каталогов и список задач.
2. Backend/Data, Ingest/Streaming, Infra/QA и Frontend shell могут стартовать параллельно, если заранее согласованы интерфейсы.
3. Chess Analysis/Feature начинает работу поверх ingest contract и feature schema.
4. FastAPI/API подключает backend и worker contracts.
5. ML agent работает на fixture/локальном Parquet, но не использует большой внешний датасет до gate подтверждения.
6. LLM agent подключается после утверждения схемы verdict.
7. Frontend agent подключается к mock API, затем к стабильному OpenAPI.
8. Infra/QA запускает интеграционные проверки после появления первого сквозного pipeline.

### Обязательный review перед merge

Ни один commit субагента нельзя вливать сразу после его завершения. Для каждой ветки координатор выполняет следующий gate:

1. Сверить diff с задачей и границами ответственности.
2. Запустить профильные unit/integration tests.
3. Передать diff отдельному критическому review-субагенту, который **не писал этот код**.
4. Review-субагент проверяет:
   - корректность;
   - регрессии;
   - обработку ошибок;
   - type safety;
   - тестовое покрытие;
   - совместимость API/DB/Parquet contracts;
   - безопасность;
   - соблюдение требований к диску, streaming и удалению PGN.
5. Если есть findings, вернуть их автору отдельной fix-задачей.
6. Автор делает исправление отдельным коммитом.
7. Критик повторно проверяет только исправленный diff и связанные тесты.
8. Координатор мержит ветку только при статусе `approved`, зелёных тестах и отсутствии блокирующих findings.

Критик не должен автоматически переписывать код автора. Его задача — найти проблемы и явно указать файл, строку, риск и рекомендуемое исправление.

### Финальный сквозной review

После merge всех основных веток координатор запускает отдельного финального проверяющего агента. Это обязательная последняя роль, не совпадающая с авторами основных модулей.

Финальный проверяющий:

- поднимает проект с чистого окружения;
- запускает миграции;
- запускает unit, integration и smoke tests;
- проверяет `POST /scans -> ingest -> analysis -> scoring -> verdict`;
- проверяет frontend flow;
- проверяет, что dataset collector:
  - не превышает 5 GiB;
  - не распаковывает архив целиком;
  - не оставляет сырые PGN;
  - пишет Parquet;
  - показывает ровно 5 строк;
  - останавливается до обучения;
- проверяет отсутствие секретов и полных PGN в логах;
- проверяет API error states и восстановление после рестарта worker;
- формирует итоговый report с блокирующими и неблокирующими замечаниями.

До устранения всех блокирующих findings релиз и merge в `main` запрещены.

### Правило merge и история коммитов

- В `main` вливает только координатор.
- Предпочтительный порядок merge:
  1. contracts и skeleton;
  2. backend/data;
  3. ingest/streaming;
  4. chess analysis/features;
  5. ML;
  6. FastAPI;
  7. LLM;
  8. frontend;
  9. infra/QA и security fixes.
- Перед каждым merge координатор обновляет ветку относительно `main` и решает конфликты вручную.
- Merge-коммит или squash обязан сохранить ссылки на исходные commit SHA субагента.
- Не использовать `git reset --hard`, удаление чужих веток или переписывание истории без явного решения координатора.
- Каждый merge сопровождается краткой записью: агент, scope, tests, reviewer, findings status.
